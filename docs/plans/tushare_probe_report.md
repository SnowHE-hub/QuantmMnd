## 2. ⚠ hk_hold 重大发现：A 股北向个股日频已于 2024-08-18 停发

**结论（对审计 §2.1 / §2.4 / §4 的修正）**

- **权限没问题**：2000 积分可调 `hk_hold`。
- **但数据源本身**：交易所于 **2024-08-18 起停止北向资金（沪深股通）个股每日持股披露**，Tushare 同步停发。此后**仅季末（03-31/06-30/09-30/12-31）单日**保留 A 股北向持股快照，平日 / 月末只返回港股通（HK）行。
- 因此 **「回补 hk_hold 2024-09→2026-05 日频」在数据源层面不可行**——这不是回补任务，而是**永久性数据限制**。本地快照已含这些季末点，无需重复拉取。
- **可行的 hk_hold 回补**：仅 **2019-01-02 → 2019-11-29 头部约 220 个交易日**（本地并集起于 2019-12-02），该窗口源端日频齐备（已确认 2019-01-02 有 2535 行含 SH/SZ）。
- **对 6 个 `north_hold_*` 因子的影响**：2024-08 之后的周频 `as_of` 只能用「最近季末」的北向持股快照（最长滞后约 60 个交易日）。这是建模必须接受的数据现实，应在特征文档中标注，**不要**误以为能靠回补补成日频。

**字段命名差异（务必处理）**：`hk_hold` 原始字段为 `vol`（持股量）/`ratio`（持股占比）。审计 §1.2 写的 `hold_vol`/`hold_ratio` 是 `tushare_provider.get_hk_hold()` 内部的别名映射（`alias={"vol":"hold_vol","ratio":"hold_ratio"}`，见 `tushare_provider.py:731`）。回补落盘时应统一 rename 为 `hold_vol`/`hold_ratio` 以与下游 `expansion.py` 的 `north_hold_*` 取数一致。

## 3. 延迟实测（悉尼 → Tushare 官方端点）

### 3.1 daily_basic 全市场（~5500 行/调，15 个不同近期 trade_date）

| 路径 | n | 均值 | 中位 | p90 | min | max | 备注 |
|------|---|-----|------|-----|-----|-----|------|
| **provider `_call`** | 15 | 7.00s | 3.73s | 25.20s | 2.24s | 27.01s | 含 `_MIN_INTERVAL=0.25s` 限频 + 重试退避；个别慢调触发 15s 读超时后重试，拉高 p90/max |
| **裸调用**（无限频/无重试/无缓存） | 15 | 5.01s | 4.23s | 7.00s | 2.64s | 15.17s | 纯网络往返，**0 报错** |

> **解读**：悉尼到 Tushare（北京）的纯网络往返，对 ~5500 行的全市场 `daily_basic`，**稳态中位 ~4.2s/调**，偶发尖刺到 ~15s（接近 provider 的 15s 读超时阈值）。provider 路径的 p90=25s 几乎全部来自「某次裸调超时 → 退避 2s → 重试」的叠加，而非每次都慢。**网络可用、够快**，但因 payload 较大，单调成本以**响应体传输**为主，而非握手延迟。

### 3.2 轻接口裸调用延迟（各 3 个近期日）

| 接口 | 实测（秒） | 中位 |
|------|----------|------|
| `margin_detail`（全市场 ~4400 行/日） | 4.03 / 4.34 / 1.96 | ~4.0s |
| `hk_hold`（~900–2600 行/日） | 1.79 / 3.91 / 2.07 | ~2.1s |
| `index_daily`（单日单指数） | 2.89 / 0.84 / 1.67 | ~1.7s |

> 行数越多耗时越大，进一步印证「payload 主导」。

### 3.3 provider 自带的节流 / 重试（报告其行为以区分网络 vs 节流）

- **限频**：`_rate_limit()` 强制最小调用间隔 `_MIN_INTERVAL = 0.25s`（`tushare_provider.py:94`）。
- **重试**：`_call()` 最多 4 次尝试，对瞬态错误（频率/timeout/connection/502/503/504/socket 等关键词）指数退避 **2 / 4 / 8s**（`:130-162`）。
- **超时**：`DataApi(timeout=15)` HTTP 读超时 + `socket.setdefaulttimeout(30)` TCP 兜底（`:28, :78`）。
- 据 3.1 对比可知：**0.25s 限频对延迟影响可忽略**（远小于 ~4s 网络时间）；provider 路径与裸调用中位差异（3.7s vs 4.2s）在抖动范围内，证明**延迟几乎全部来自网络/payload，而非 provider 节流**。

## 4. 频率行为与限速建议

- **测法（温和，不刻意 burst 到失败）**：用 20 个不同近期 trade_date 连发**裸** `daily_basic`（无 sleep），观察是否自然触发限频。
- **结果**：20 次全部成功，**0 次限频/权限报错**；总耗时 **95.98s**，有效速率 **12.5 调/分钟**——这个速率是**网络往返（~4.8s/调）自然形成的**，并非被服务端限频压制。
- 因此**未观察到 2000 积分对这些接口的每分钟硬限**（在此温和强度下）。瓶颈是**单调网络延迟**，不是配额。

**保守限速建议（用于回补）**

| 项 | 建议值 | 理由 |
|----|-------|------|
| 最小调用间隔 | **0.5s**（即理论上限 120 调/分钟） | 远低于 2000 积分配额、也高于网络实际允许的 ~12–15 调/分钟，纯属安全垫；沿用 provider `_rate_limit` 思路，可把 `_MIN_INTERVAL` 由 0.25→0.5 |
| 每分钟上限（保守） | **≤ 120 调/分钟** | 即便网络变快也不越界；实际因 payload 较重，daily_basic 全市场顺序执行只会跑到 ~12–15/分钟 |
| 退避 | 指数退避 2/4/8（→ 可加 16s 第 4 档），最多 5 次 | provider 已具备；对偶发 15s 超时与瞬态错误足够 |
| 读超时 | 维持 15s + socket 30s | 与实测 max(15.2s) 吻合；过短会误杀偶发慢调 |

## 6. 回补策略建议（含断点续传设计）

### 6.1 拉取模式

- **按 trade_date 循环、每日一调、全市场一次返回**（`daily_basic`/`margin_detail`/`hk_hold` 均支持 `trade_date` 全市场拉取，实测见 §1）。比按 `ts_code` 逐只快 ~1000×。
- 交易日历来源：用 `index_daily(000300.SH)` 的 `trade_date` 序列，或 `trade_cal(is_open=1)`，生成待拉日期集合（本探针即用前者获取近 40 个交易日）。

### 6.2 落盘为连续日频数据湖表（非季度快照）

```
data/lake/daily_basic.parquet      # (ts_code, trade_date) 全历史日频
data/lake/margin_detail.parquet
data/lake/hk_hold.parquet          # 落盘前 rename vol→hold_vol, ratio→hold_ratio；仅含 ≤2024-08-16 日频 + 季末点
data/lake/_checkpoints/<series>.json
```

- 与审计/面板方案一致：连续日频湖表，下游周频重采样按 `trade_date ≤ as_of` 直接切窗。
- 建议分区可选：按年分目录（`data/lake/daily_basic/year=2019/...`）以便增量与并发；首版单文件亦可。

### 6.3 断点续传（checkpoint）

- 状态文件 `data/lake/_checkpoints/<series>.json` 记录**已完成的 trade_date 集合**（及每日行数、写入时间戳、源接口）：
  ```json
  {"series":"daily_basic","done":["20190102","20190103", "..."],
   "rows":{"20190102":3555}, "updated":"2026-06-05T...", "source":"tushare.daily_basic"}
  ```
- 重启时：`待拉 = 全交易日集合 − done`，**跳过已完成日期**，实现「断哪续哪」。
- checkpoint 与 parquet **同批落盘**（先写数据再更新 checkpoint），避免「标记完成但数据未落」。

### 6.4 幂等

- 主键 **(ts_code, trade_date)**；写盘前对该键去重（`drop_duplicates(subset=["ts_code","trade_date"], keep="last")`）。
- 重跑任意已完成日期安全：要么被 checkpoint 跳过，要么覆盖写同键不增行。

### 6.5 增量写盘

- **每完成一个交易日（或每完成一个月一批）立即落盘** + 更新 checkpoint。崩溃最多丢「在途的一批」，已落盘部分不受影响。
- 推荐「按月成批」：积累一个月的日频后 append 到湖表，减少小文件 / 写放大；checkpoint 仍按天记录粒度。

### 6.6 健壮性（限频 / 网络错误）

- **复用 `tushare_provider._call`**：已含限频（0.25s，建议提至 0.5s）+ 瞬态错误指数退避（2/4/8s，建议加 16s）+ 15s/30s 超时（§3.3）。
- 对单日多次重试仍失败者：记入 `_checkpoints/<series>.failed.json`（日期 + 错误原文），**不阻塞**整体进度，跑完后单独补这些日期。
- 实测 p90 偶发 ~15–27s 慢调属正常（§3.1），退避机制已能吸收，**不需**降速到极端保守。

### 6.7 对审计 §4 的落地修正小结

| 序列 | 审计原计划 | 本探针修正后建议 |
|------|-----------|----------------|
| daily_basic | 全程 2019-2026 日频回补 | ✅ 照办（~1762 日，2–3.5h） |
| margin_detail | 2019 头部 ~220 日 | ✅ 照办（~220 日，~15–26min） |
| hk_hold | 2024-09→2026-05 日频 + 2019 头部 | ⚠ **仅回补 2019 头部 ~220 日**；2024-09 之后**源端无日频**（仅季末，本地已有），不可回补——改为「特征文档标注：北向个股持股 2024-08 后退化为季末频」 |
| index_daily | 无需（可选 2019 头部 ~33 日） | 维持；可选顺带补头部 |
