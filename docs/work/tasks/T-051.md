# T-051 · A1 Harness v3：可读金额、完整性检查、文字字段核对；留出集 2 上重测 DeepSeek 与本机 9B

- 起因（2026-10-23 晚）：
  - X7 v1.2：本机 9B 工具循环，召回 34.3%；
  - X7b：本机 9B 单次调用，前 14 个案例召回 46.9%。
  - 错误集中在三类：
    1. 元 → 亿元换算错一个数量级（543.34 亿 vs 54.33 亿）；
    2. 漏写上年同期的营收和归母净利润（14 个案例里漏 12–13 次）；
    3. 审计意见、业绩预告类型这类文字字段，模型用 value = 1.0 加字段名引用，校验器核不了。
  - DeepSeek 也有第 2 类问题：留出集上最常漏的是"最近一次业绩预告的类型"。
- 分支：`t/035-line-a-v2-p0`，不推送。

## 登记（2026-10-23 22:5x，在实现和运行之前）

### Harness v3 的三处改动
1. **可读金额**：工具返回的金额字段另附 `_display`（例如 `"revenue": "54.33亿元"`），由代码换算。模型可以直接照抄，不用自己换算单位。
2. **完整性检查**（只针对 A1，代码实现）：角色输出通过 Schema 校验之后，代码检查 A1 提示词 v2 规定"必须覆盖"的几项有没有写到：
   - 最新报告期和上年同期的营业收入、归母净利润（引用对应期间的利润表记录）；
   - as_of 前 120 天内的业绩预告类型（工具返回了预告才要求）；
   - 最近一份年报的审计意见（工具返回了审计记录才要求）。
   - 缺了就把缺失清单发回去，让模型补一次、输出完整 JSON。只补一次，补完不再检查；
   - 只检查"有没有写"，不检查数值，数值仍由校验器核对。
3. **文字字段核对**（校验器）：引用的字段在记录里是文字（如 audit_result、forecast 的 type）时，核对声明正文或引文里有没有出现记录里的这段文字。

### 评测：A1 留出集 2（新）
- 原来的留出集已经在 X7、X8、X10 里用过很多次，这次的改动又是看着它的错误设计的，所以另抽一个新集合：
  - 种子 20261026；
  - 时点 2025-09-10、2025-11-10、2026-05-11、2026-09-10，与开发集、留出集都不重叠；
  - 每个时点 10 个案例，共 40 个；
  - 同一份标准事实和打分函数。
- 三组：

  | 组 | 后端 | Harness |
  |---|---|---|
  | B | DeepSeek | 单次调用（当前默认） |
  | V | DeepSeek | 单次调用 + v3 |
  | L | 本机 9B | 单次调用 + v3，关闭思考，32K，约束解码 |

### 判定
- **v3 用于 DeepSeek**：V 的召回不低于 B 1 个百分点以上，且有问题声明不高于 B 0.5 个百分点以上。
- **本机 9B 作为 A1 的降级后端**（DeepSeek 不可用时，例如校园网）：
  - L 的召回不低于 V 5 个百分点以上；
  - 有问题声明不高于 V 2 个百分点以上；
  - 弃答 ≤ 10%。
- 先跑 L（不需要外网）；B、V 等网络恢复后跑。

### 实现说明（2026-10-24 01:xx，在任何 B / V / L 运行之前；属于实现细节，判定规则不变）
- 开关：`run_slice(..., v3=True)`。打开后：
  - `DataTools.display_amounts = True`；
  - 任务文本里加一句：正文写金额时照抄 `_display`，value / unit 仍按原始字段；
  - A1 挂上 `completeness.a1_missing`；
  - 默认关闭，判定通过后再在每日研究里打开。
- 完整性补充的机制：
  - 单次调用的最大轮数从 3 改为 4，留出补充那一轮；
  - 补充那一轮不合格时，用补充之前已经合格的输出，不记弃答（不让完整性检查把原本合格的回答变成弃答）。
- **文字字段核对属于校验器**，三组（B、V、L）都用同一个校验器 v3 打分，所以 B 组也按它打分。
  - 这样三组之间可比；代价是 B 组的分数和 X8 不能直接比较；
  - 生产校验器同时升级（只会更严格）；
  - 只对短文字字段生效（≤ 30 字，排除纯数字串、日期和证券代码）。
- 脚本：`scripts/line_a/run_t051.py --arm B|V|L`。
  - 输出 `data/line_a_v2/eval/t051_{B,V,L}_holdout2/`；
  - 留出集 2 的案例写在 `cases.json`。
- 顺序：
  - B、V 先跑（DeepSeek，现在网络可用）；
  - L 等每日运行的显卡步骤结束后跑（本机 9B 要占满显存）。

### 第一次运行中止：工具结果截断的问题（2026-10-24 01:0x）
- **现象**：
  - V 组第 1 个案例召回只有 0.6，营业收入写成了记录里没有的数；
  - 补充那一轮模型说"revenue 字段数值未在结果中显示（记录被截断）"。
- **原因**：单次调用和工具循环都把每个工具结果截到 12,000 个字符。
  - `canonical` 按键名排序，`financial_snapshot` 里利润表（income）排在最后；
  - 默认 8 期本来就有约 12,600 字符，**B 组、生产、X8、X7b 都被截掉了利润表最后约 600 字符**，也就是最旧的一期左右；
  - v3 加上 `_display` 后到了约 15,800 字符，利润表大半被截掉。
  - 这是 harness 的问题，与 v3 的设计无关。
- **修正**（三组共用）：
  - 上限改为 24,000；
  - 超长时按结构截断：从最长的列表末尾（最旧的记录）逐条删，JSON 保持合法，并写明删了几条；
  - 证据只登记模型实际看到的记录。
- 中止时 B 已跑 3 个案例、V 已跑 1 个。这两份输出移到 `t051_{B,V}_holdout2_aborted_trunc/` 保留，不参与判定；B、V 用新目录从头重跑。
- 对以前结果的影响：X8 / X7b 的 A1 输入里，最旧一期左右的利润表被截掉。标准事实只用最新一期和上年同期，所以影响应该很小，但没有重跑，这里如实记下。
