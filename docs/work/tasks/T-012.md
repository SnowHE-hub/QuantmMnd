## 背景与证据
- [实测] `data/raw/alpha_prices_panel.parquet`、`alpha_prices_panel_v6.parquet` 与 `quantmind.data.lake.load_trading_calendar()`
  都只有 1,762 个交易日，比快照交易日并集少 18 个真实交易日（如 2021-03-05～03-15、2021-06-10、2023-03-16、2023-06-16、2026-03-03）。
- [实测] `data/alpha_universe/price_date_done.txt` 有 1,780 行，**这 18 天都在里面**——被标成已完成，但数据没写进去。
- [代码] `scripts/data_pipeline/step2_download_prices.py`：
  - `_retry`（:92-105）在重试耗尽时吞掉异常、返回空表；
  - `run_by_date`（原 :257-260）把空表当作"可能非交易日"并 `done_dates.add(dt)`；但日期来自 `trade_cal(is_open=1)`，一定是交易日。
  - 结果：任何一次请求失败的交易日都被永久跳过。

## 改动
- 空表 = 失败：不记入 done，计入 `failed_dates`，结束时打印；下次运行自动重试。
- 新增 `tests/test_download_prices_done_marking.py`（假 API 驱动 `run_by_date`）：
  修复后 3 passed；**在原代码上 2 failed**（"空表不标记完成"与"下次重试"），证明测试抓得住这个 bug。`[实测]`

## 顺带发现（[推断]，未在本卡处理）
`_flush_date_parts`（本分支 :334 起，main :325 起）在函数末尾 `new_parts.clear()`，清空的是调用方的 `date_parts` 同一个列表对象；
因此 `run_by_date` 结尾"合并复权因子"那一步只拿得到最后一批（<100 天）的日线。是否因此有复权口径不一致，需要单独核对 `_save_panel` 的行为。
